# AI 运维能力产品规划

> 状态：**待规划**（功能池文档，尚未排期；实施前需按阶段拆分实现计划）
> 产生背景：2026-07-09 UI 改版完成后，围绕产品定位「一款具备 AI 运维能力的 SSH 客户端」的交互功能讨论沉淀。
> 相关文档：`ssh-client/docs/UI-DESIGN.md`（视觉/动效规范）

## 产品定位

一款具备 AI 运维能力的 SSH 客户端。与「SSH 客户端旁边挂一个通用聊天窗」的本质区别：**AI 能看到终端里发生了什么，并能把结论安全地送回终端执行**。

核心信任原则（所有功能设计的红线）：

1. **命令在执行前永远可见、可编辑**——AI 生成的命令只预填不自动回车（只读巡检类除外，见 F7/F8）。
2. **写操作必须人工确认**——Agent 模式下只读命令可自动执行，任何变更类操作必须点击确认。
3. **高危命令强制防呆**——无论命令来自 AI 还是用户手输，统一走危险模式识别与确认。

## 关键前提（P0，一切功能的地基）

### F0. 真实 AI 通道

当前 `chatStore` 走 `utils/mockAi.ts` 假实现。所有 AI 功能的第一步是后端建立真实 AI 对话通道：

- **后端**：新增 AI 对话端口（延续 DDD 端口模式，`domain` 定义 `IAiChatPort`，`infrastructure` 实现，对接大模型 API）；支持对话历史与「终端上下文」透传；流式返回（SSE 或轮询，与现有终端输出轮询风格对齐可先用轮询）。
- **前端**：`chatStore.sendMessage` 从 mockAi 切换到真实 API；已就绪的流式打字动画（`freshId` + typewriter）直接消费真实流。
- **待决策**：接哪家模型 / 是否支持自定义 API 地址与 key（运维工具用户大概率有私有化诉求，建议设置面板支持自定义 baseUrl + key，与现有「后端地址设置」同级）。

## 第一层：胶水交互——终端与 AI 面板握手（建议最先做）

组成最小魔法闭环：**看到报错 → 一键问 AI → AI 给命令 → 一键插回终端**。纯前端 + F0 即可实现，不动终端会话架构。

### F1. 选中即问

- **交互**：终端内选中文本 → 选区附近浮出「问 AI」小按钮 → 点击后选中内容 + 简短前后文自动作为引用块进入聊天输入框，焦点切到 AI 面板。
- **价值**：压缩运维最高频动作链（看到报错→复制→切窗→粘贴→描述）为一步。
- **技术要点**：xterm `onSelectionChange` + `getSelection()`；引用块在 MessageBubble 渲染为可折叠样式。

### F2. AI 回复中的命令块可执行

- **交互**：AI 回复中的 shell 代码块渲染为命令卡片，带三个动作：**插入终端**（预填当前激活终端的输入行，不回车）、**复制**、**解释**（追问该命令逐段含义）。
- **价值**：AI 的输出直接变成可用的操作，闭环最后一公里。
- **技术要点**：消息内容 markdown 解析（当前 MessageBubble 是纯文本渲染，需引入轻量 md 渲染）；「插入终端」经 terminalManager 向激活会话写入命令文本（不含换行符）。

### F3. 终端上下文快照

- **交互**：聊天输入栏增加「附带终端上下文」开关（默认关）；开启时发送消息自动附当前激活终端最近 N 行（建议 50，可配置）输出。
- **价值**：AI 回答「为什么起不来」类问题时有真实依据。
- **技术要点**：xterm buffer 读取最近行；上下文以系统消息形式进 prompt，不在气泡中完整显示（显示为「已附带终端上下文 · 50 行」小标签）。
- **隐私注意**：上下文可能含敏感信息（密钥、内网地址），默认关 + 显式标签是刻意设计。

## 第二层：核心差异化——AI 渗入终端本体

### F4. 自然语言转命令（inline AI，Ctrl+K）

- **交互**：终端内按 `Ctrl+K` → 输入行上方浮出自然语言输入条（AI 渐变描边，视觉上与普通输入区分）→ 输入「找出占用 8080 端口的进程并杀掉」→ AI 返回命令预填入终端当前行并高亮 → 用户可编辑，回车才执行，Esc 取消。
- **价值**：用户不离开终端、不切面板，「AI 味」进入核心工作流；Warp 已验证该路线。
- **依赖**：F0；快捷键与 xterm 按键处理的冲突需处理（`attachCustomKeyEventHandler`）。

### F5. 报错自动诊断气泡

- **交互**：检测到命令失败信号（exit code 非 0 或输出匹配 error 模式）→ 终端右下角浮现不打扰的小气泡「AI 已定位可能原因」→ 点击展开诊断卡片（原因 + 建议命令，命令复用 F2 卡片）→ 不点击 3 秒淡出。
- **价值**：从「用户主动问」进化到「AI 主动帮」，且以不打扰为前提。
- **技术要点**：exit code 获取需要 shell 集成（PROMPT_COMMAND / PS1 注入）或退化为输出模式匹配；建议先做输出匹配版。
- **防噪**：同类报错短时间内不重复弹；提供全局开关。

### F6. 危险命令防呆

- **交互**：识别高危模式（`rm -rf` 变体、`drop database`、裸 `chmod -R 777`、`mkfs`、`> /dev/sda` 等规则库）→ 回车时弹确认卡片：显示命令、危险原因、影响范围提示，需显式点击「仍然执行」。
- **价值**：「AI 不会帮用户删库」的信任感是 AI 运维产品的生命线；该防线同时覆盖 AI 生成与人工输入。
- **技术要点**：前端拦截回车 + 规则匹配即可起步；规则库做成可配置（允许用户关闭单条规则或整体）。
- **注意**：拦截点在「回车提交前」，与 F2「插入不执行」、F4「预填不执行」共同构成三层安全设计。

## 第三层：远期愿景——Agent 化运维

### F7. 任务式 Agent

- **交互**：聊天面板输入目标（「查一下这台机器为什么磁盘满了」）→ AI 进入 Agent 模式，循环「生成命令 → 执行 → 读输出 → 决策下一步」；每一步在聊天面板渲染为步骤卡片（命令 + 输出摘要 + 状态）。**只读命令自动执行，写操作卡片带确认按钮暂停等待。**
- **价值**：真正的「AI 运维」，是产品护城河；但对模型能力、安全设计、失败恢复要求高，不宜早做。
- **架构备注**：现有「后端持有 SSH 会话 + 前端轮询」天然适合——Agent 循环放后端（复用 `ISshSessionPort`），前端只渲染步骤流；命令只读/写操作分类可先用规则 + 模型自评双通道。

### F8. 连接后自动巡检

- **交互**：SSH 连接建立后，后台静默执行固定的只读巡检命令组（`uptime` / `df -h` / `free -m` / `top -bn1 | head`）→ 结果摘要显示为连接卡片上的健康小标（如磁盘 92% 标红）；点击小标展开完整巡检报告。
- **价值**：打开终端前就知道机器状态；连接列表从「地址簿」升级为「监控面板」。
- **技术要点**：巡检命令组固定白名单、只读、可全局关闭；在后端连接建立流程后异步执行，不阻塞终端打开。

## 建议优先级与依赖关系

| 优先级 | 功能 | 依赖 | 主要工作面 |
|---|---|---|---|
| P0 | F0 真实 AI 通道 | — | 后端为主 |
| P1 | F1 选中即问 | F0 | 前端 |
| P1 | F2 命令块可执行 | F0 | 前端 |
| P1 | F3 终端上下文快照 | F0 | 前端 |
| P2 | F6 危险命令防呆 | 无（可独立先行） | 前端 |
| P2 | F4 Ctrl+K 自然语言转命令 | F0 | 前端 + 后端 |
| P2 | F5 报错自动诊断气泡 | F0、F2 | 前端 |
| P3 | F8 连接后自动巡检 | — | 后端 + 前端 |
| P3 | F7 任务式 Agent | F0、F2、F6 | 后端为主 |

说明：
- F6 不依赖 AI，可作为独立小功能穿插实现；
- F1+F2+F3 构成第一个可发布的「AI 运维」故事，建议作为 F0 之后的第一个迭代整体交付；
- F7 需要 F6 的安全设施和 F2 的卡片组件成熟后再启动。

## 待决策问题（规划时需拍板）

1. **模型接入方式**：接哪家 API；是否支持用户自定义 baseUrl/key（建议支持，运维用户私有化诉求强）。
2. **流式方案**：SSE 还是沿用轮询风格（与现有终端输出轮询一致性 vs 技术先进性）。
3. **上下文隐私策略**：终端上下文是否需要脱敏（如自动掩码形如密钥/密码的 token）后再发送。
4. **F5 的失败检测方案**：shell 集成（准确但侵入）vs 输出模式匹配（简单但有误报），建议先后者。
5. **多终端场景**：F3/F4 的「当前终端」始终指激活 tab，多 tab 并发 Agent（F7）是否允许，建议首版单会话。
