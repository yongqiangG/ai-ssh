# LLM 配置保存后的上一版回滚

## 原始需求

> 当前client端的chat面板可以配置llm的调用信息，现在我想增加配置回滚功能，可以回滚到上一个版本的功能。
> 主要应对的场景是，我配置成其他的llm信息，如果发现无法正常使用可以快速回滚。
> 我感觉这个功能可以直接做在client端就可以，如果应用退出，就不提供这个回滚功能。核实下 grill me

## 背景

- client 的 `LlmSettingsModal` 通过 `/api/v1/llm-config` 读写配置；配置实际持久化在 server，GET 响应只返回 `apiKeyConfigured`，不会返回原始 API Key。
- server 当前只维护一个 `default` LLM 配置，并在配置变化后重建 runner；client 已有发送中/工具调用拦截和 runner 重建后的会话归档逻辑。
- 若只在 client 保存上一版，首次修改已有配置时无法取得旧 API Key；因此完整回滚必须由 server 暂存完整快照，且不能落盘或回传敏感字段。

## 决议

1. **问题：回滚是否包含 API Key？** 结论：恢复 `providerName`、`baseUrl`、`model`、`completionsPath` 和 API Key 的完整配置；理由是只恢复非敏感字段无法保证原配置可用。
2. **问题：快照放在哪里？** 结论：由 server 在进程内存暂存上一版，client 负责入口和展示；理由是 server 才能安全取得并恢复旧 API Key，同时不把密钥交给 client。
3. **问题：保留多少版本？** 结论：只保留一个上一版槽位，回滚成功后清除；理由是需求是一步回退，避免实现完整历史和来回切换。
4. **问题：什么算新版本？** 结论：实际配置变化才覆盖槽位；首次无 Key 配置不生成快照，无变化保存保留现有槽位；理由是没有可恢复的完整旧配置时不应显示回滚。
5. **问题：快照生命周期与隔离范围是什么？** 结论：以 server 进程生命周期为准，仅支持一个 client 对应一个 server；理由是现有 LLM 配置使用全局 `default`，扩大到多用户隔离会改变范围。
6. **问题：回滚从哪里触发？** 结论：在现有模型设置弹窗增加手动回滚入口，GET 响应增加状态/摘要，新增独立 rollback API；理由是复用现有入口并保持保存接口兼容。
7. **问题：是否自动探测或自动回滚？** 结论：不做 LLM 连通性探测和自动回滚；理由是超时、限流和网络故障不等价于配置错误，且不同供应商探测语义不一致。
8. **问题：如何防止覆盖更新后的配置？** 结论：server 校验当前配置仍匹配快照对应的保存后配置，否则拒绝回滚；理由是回滚不能覆盖外部或并发产生的新配置。
9. **问题：回滚期间如何处理会话？** 结论：发送中或有运行/待确认工具调用时禁止回滚，成功后沿用配置切换规则归档当前活动会话并新建会话；理由是避免一个会话混用不同 runner 的上下文。
10. **问题：失败如何处理？** 结论：回滚只有配置恢复和 runner 重建都成功才清除快照；失败返回明确错误并保留恢复能力。现有保存链路不做整体原子性重构，runner 重建半成功时保留旧快照供恢复；理由是控制改动范围同时保留故障自救路径。
11. **问题：敏感字段如何保护？** 结论：API Key 只在 server 内部处理，不经 DTO 返回、不写日志、不写浏览器存储；理由是回滚能力不应扩大密钥暴露面。
12. **问题：未保存草稿、重复点击如何处理？** 结论：回滚丢弃未保存草稿；保存/回滚请求互斥并在 client 禁止重复点击；理由是版本只代表已保存状态，避免重复重建和状态竞态。

## 影响范围

- server：增加进程内上一版 LLM 配置快照、回滚状态摘要、独立回滚接口、并发/陈旧配置校验和对应单元测试；保持现有配置持久化结构与保存接口兼容。
- client：扩展 LLM 配置 API 类型，在设置弹窗展示上一版摘要和手动回滚操作，复用现有 agents 刷新、错误处理和会话归档流程。
- 安全与生命周期：API Key 不离开 server；server 重启、sidecar 随应用退出后回滚快照失效；共享 server/多 client 并发不在本次范围内。
